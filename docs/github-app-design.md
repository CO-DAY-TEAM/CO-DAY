# CO-DAY GitHub App 최종 설계

이 문서는 CO-DAY GitHub App 설계의 유일한 최종본이다. 설계 변경은 이 문서에 직접 반영한다. 본문은 구현할 동작과 완료 기준을 정의하고, 후속 결정과 제외 항목은 각각 11장과 12장에서 관리한다.

## 1. 목표와 제공 기능

GitHub.com의 개인·조직 계정이 설치하여 public·private 저장소의 실제 PR을 리뷰할 수 있는 GitHub App을 CO-DAY에 구현한다.

리뷰 결과와 진행 상태는 GitHub PR에서 확인하고, 대시보드는 로그인·설정·저장소 및 리뷰 목록·실패 재시도·통계를 제공한다. 서비스의 사용자 대상 문구와 리뷰는 한국어로 작성한다. 기술 용어와 코드 식별자는 원문을 유지한다.

| 항목 | 확정 범위 |
| --- | --- |
| GitHub 지원 | GitHub.com, 개인·조직 설치, public·private 저장소 |
| 리뷰 분야 | 버그, 보안, 스타일, 유지보수성 |
| 프로그래밍 언어 | 언어 제한 없이 입력을 받으며, 언어에 따라 리뷰 품질은 달라질 수 있음 |
| 리뷰 언어 | 한국어 고정 |
| AI 인증 | 서비스 측 API 키 사용 |
| 검증 | 실제 PR에서 주요 기능과 실패 복구 확인 |

## 2. 사용자 경험

1. 사용자가 GitHub로 로그인하고 자신의 개인 계정 또는 조직에 App을 설치한다.
2. GitHub에서 허용한 저장소에 대해 대시보드에서 공통 설정 또는 저장소 독립 설정을 관리한다.
3. 대상 PR 이벤트 또는 권한 있는 사용자의 리뷰 명령으로 실행을 시작한다.
4. GitHub PR의 동일한 진행 상태 댓글을 수정하여 대기·진행·완료·실패를 안내한다.
5. 분석 대상 전체의 처리가 성공하면 리뷰 결과를 게시한다. 중요한 문제는 인라인, 가벼운 개선 제안은 요약에 모은다.
6. 실패하면 같은 진행 댓글에서 대시보드의 해당 실패 항목으로 이동할 수 있다. 로그인·권한 확인 후 재시도 버튼으로 이어서 처리한다.
7. 대시보드에서는 PR 목록을 통해 GitHub로 이동하고, 리뷰한 PR 수와 게시 지적 통계를 확인한다.

실패 이유와 재시도 버튼은 대시보드의 해당 리뷰 목록 항목에서 제공한다. 코드와 리뷰 내용은 GitHub PR 페이지에서 확인한다.

## 3. 설정과 권한

### 설정 단위

‘공통 설정’은 App이 설치된 **개인 계정 또는 조직 하나**에 속한다. GitHub API에서는 계정별 App 설치를 `installation`으로 구분하며, 각 installation의 설정은 독립적으로 관리한다.

| 설정 | 동작 |
| --- | --- |
| 자동 리뷰 | 기본 ON. OFF여도 권한 있는 사용자의 수동 리뷰·실패 재시도는 가능 |
| 추가 리뷰 지침 | 대시보드에서 선택적으로 입력. 비어 있으면 서비스 기본 기준, 입력하면 기본 기준에 추가 반영 |
| 제외 경로 | 기본 제외 규칙과 사용자 지정 규칙으로 분석 대상을 조정 |
| 개인·조직 전체 중지 | 별도 제어. 해당 installation의 새 자동·수동·재시도를 모두 막으며 저장소 설정으로 우회 불가 |

추가 지침은 대시보드 설정에서 입력받는다. 앱 권한, 실행 범위, 한국어 출력 정책은 추가 지침보다 우선한다.

### 공통 설정 사용 방식

- 저장소의 ‘공통 설정 사용’은 기본 ON이다. 설정 묶음 전체가 공통 설정을 따르고 이후 공통 변경도 반영한다.
- OFF로 전환하면 현재 공통 설정을 초기값으로 복사하고, 저장소가 설정 묶음 전체를 독립적으로 관리한다.
- 다시 ON으로 전환하면 저장소 독립 설정을 버리고 공통 설정을 따른다. 버려지는 설정이 있음을 안내한다.
- 저장소 독립 설정의 추가 지침을 비우면 서비스 기본 기준을 사용한다.

### 권한

| 행동 | 필요한 사용자 권한 |
| --- | --- |
| 개인 계정의 공통 설정·전체 중지 변경 | 개인 계정 소유자 |
| 조직의 공통 설정·전체 중지 변경 | 조직 Owner |
| 저장소 독립 설정 변경 | 해당 저장소 Admin |
| 수동 리뷰·실패 재시도 | 해당 저장소 Write 이상 |
| 대시보드 목록·설정 조회·통계 열람 | 해당 저장소에 대한 명시적 접근 권한 |

public 저장소라는 이유만으로 외부 사용자에게 대시보드를 공개하지 않는다. 통계도 사용자가 접근 가능한 저장소만 집계한다. GitHub App의 접근 권한과 요청한 사용자의 권한을 각각 확인한다.

## 4. 실행 시점과 중지

### 자동·수동 실행

| 상황 | 정책 |
| --- | --- |
| `draft=false`인 PR의 `opened` | 자동·수동 리뷰 실행 기록이 없을 때 최초 1회 자동 리뷰 |
| draft PR의 `ready_for_review` | 자동·수동 리뷰 실행 기록이 없을 때 최초 1회 자동 리뷰 |
| 이미 자동 또는 수동 리뷰한 PR의 `ready_for_review` | 자동 리뷰하지 않음 |
| 자동 리뷰 설정을 ON으로 변경 | 설정 변경만으로 리뷰를 시작하지 않으며, 기존 리뷰 실행 기록을 초기화하지 않음 |
| 새 커밋 추가·suggestion 적용으로 인한 `synchronize` | 자동 리뷰하지 않음. 추가 리뷰는 댓글로 요청 |
| `reopened` | 자동 리뷰하지 않음 |
| draft PR | 수동 리뷰만 |
| bot이 작성한 PR 또는 fork PR | Write 이상 사용자가 요청한 수동 리뷰만 |
| 완료된 동일 커밋의 수동 리뷰 | 현재 설정으로 새 리뷰 허용 |
| 동일 PR·커밋의 작업이 대기·진행 중 | 중복 실행 생성 차단 |

GitHub App 이름은 `co-day-review`이며, PR의 일반 댓글(`issue_comment`)에 `@co-day-review review` 명령을 입력해 리뷰 실행을 요청한다. 실패한 실행을 이어가는 진입점은 대시보드다.

최초 자동 리뷰 여부는 저장소 ID와 PR 번호에 해당하는 모든 리뷰 실행 기록으로 판단한다. 자동·수동 어느 경로든 작업을 대기열에 등록한 기록이 있으면 자동 리뷰를 추가로 시작하지 않는다. 실패·취소되거나 커밋·자동 리뷰 설정이 바뀌어도 이 기록을 초기화하지 않으며, 서버를 재시작해도 DB 기록을 유지한다. 추가 리뷰는 댓글로 요청하고, 실패한 실행의 재시도는 기존 실행 기록을 이어서 처리한다. 자동·수동 구분은 설정 변경 시 대기 작업 취소 등 실행 정책에 사용한다.

### 실행 중 변경

| 제어 | 새 작업 | 대기 작업 | 이미 실행 중인 작업 |
| --- | --- | --- | --- |
| 자동 리뷰 OFF | 자동만 차단. 수동·재시도 허용 | 자동 기원 작업 취소 | 완료까지 진행하고 결과 게시 |
| 개인·조직 전체 중지 | 자동·수동·재시도 모두 차단 | 모두 취소 | 완료까지 진행하고 결과 게시 |
| App 제거·저장소 접근 해제 | 실행·조회·재시도 차단 | 실행 불가 | 추가 접근·게시 중단 |

중지를 해제해도 취소된 대기 작업을 자동으로 복원하지 않는다. 취소된 PR의 추가 리뷰는 댓글로 요청한다.

실행 중 새 커밋이 들어와도 자동으로 새 리뷰를 시작하지 않는다. 게시하지 않은 오래된 head의 결과를 뒤늦게 게시하지 않으며, 최신 커밋의 리뷰는 댓글로 요청한다. ‘실행 중이면 끝까지 완료’ 정책도 현재 권한과 최신 head에 대한 검증을 우회하지 않는다.

위 정책을 구현할 때는 webhook과 작업 실행·게시 전 권한 재검증으로 접근 해제를 확인한 즉시 추가 처리를 차단한다. GitHub의 변경 순간과 CO-DAY의 인지 시점이 항상 같거나, 이미 외부에 접수된 요청까지 회수할 수 있다고 보장하지 않는다.

게시 직전 PR의 head SHA를 다시 확인하고 변경을 발견하면 해당 게시를 중단한다. 리뷰의 `commit_id`도 분석한 SHA로 지정한다. 다만 head SHA 확인 직후 발생한 새 커밋과 GitHub 게시를 하나의 원자적 작업으로 제어할 수는 없다.

## 5. 분석 범위와 결과

### 입력과 조사 범위

- 매번 최신 PR 전체 diff를 대상으로 한다.
- 수동 새 리뷰는 이전 리뷰 결과를 판단 자료로 사용하지 않고 현재 코드와 설정으로 새로 분석한다.
- 변경 파일을 중심으로 같은 저장소의 관련 코드·타입·테스트를 필요에 따라 찾아 읽는다.
- 테스트 파일도 판단을 위한 읽기 자료로 활용한다.
- 지적은 이번 PR이 만든 문제를 대상으로 한다.
- 원본 커밋과 사용한 설정을 실행에 고정해 저장한다. 재시도 중 입력과 판단 조건이 섞이지 않게 한다.

### 파일 필터링과 완료 기준

- lockfile, 바이너리 파일, `node_modules`, 생성된 파일을 모은 디렉터리를 기본 제외한다.
- 소스·설정·테스트·문서는 분석 대상이 될 수 있다. 텍스트 파일 제외 규칙은 사용자가 조정할 수 있게 한다.
- 완료는 **제외 규칙 적용 후 분석 대상으로 정한 범위 전체가 정상 처리됨**을 뜻한다.
- 결과에는 분석·제외 파일 수와 제외 사유를 안내한다.
- 분석할 파일이 없으면 AI를 호출하지 않고 ‘완료 · 리뷰 대상 없음’으로 안내한다. 이를 ‘문제가 없는 코드’로 표현하지 않는다.
- 분석했지만 지적이 없으면 인라인 댓글 없이 ‘완료 · 지적 없음’을 안내한다.
- 필요한 파일을 가져오거나 분석하는 데 실패한 경우를 단순 제외로 바꾸어 완료 처리하지 않는다.

완료는 서비스의 처리 성공을 의미하며, 코드에 결함이 전혀 없다는 보증은 아니다.

### 게시할 내용

- 문제 발생 조건과 코드 근거를 설명할 수 있는 지적만 게시한다.
- AI 응답은 발생 조건·코드 근거·수정 방향·교체 코드를 별도 필드로 받으며, 댓글의 제목·문단·suggestion 블록은 서버가 구성한다.
- 설명에는 짧은 인라인 코드만 허용하고 전체 교체 코드는 suggestion에만 둔다. 교체 코드가 없으면 null로 저장하고 해당 블록을 표시하지 않는다.
- Pydantic으로 필수 필드·자료형·길이를 검증하고, 지적한 파일·줄·수정 범위가 실제 diff에 해당하는지 확인한다. 응답 형식이나 지적 위치 검증에 실패하면 AI를 자동으로 다시 호출하지 않고 실패 처리한다. 사용자는 대시보드에서 재시도할 수 있다.
- 중요한 문제와 명시적인 리뷰 규칙 위반은 인라인으로 남긴다.
- 정확하고 작은 교체 코드를 제안할 수 있으면 같은 인라인 댓글에 suggestion 블록을 추가한다.
- 수정 코드가 없어도 중요한 문제는 설명형 인라인 댓글로 남길 수 있다.
- 가벼운 개선 제안은 요약에 모은다. 각 지적은 무엇이 문제인지와 수정 방향을 설명한다.
- GitHub 리뷰는 `event=COMMENT`로 게시한다.
- 사용자가 GitHub의 **Apply suggestion**으로 PR 브랜치에 수정 내용을 커밋한다.
- 이전 리뷰에서 지적한 문제라도 현재 코드에 남아 있으면 새 리뷰 결과에 게시한다. 과거 게시 여부로 지적을 제외하지 않는다.
- 기존 review thread는 사용자가 GitHub에서 정리한다.

## 6. 실패와 재시도

사용자에게 표시하는 리뷰의 최종 결과는 완료 또는 실패다. 정해진 분석 범위 전체의 처리가 성공한 뒤 결과를 게시한다.

1. 실행 중 성공한 단계·분석 단위의 결과를 내부에 저장한다.
2. 일시적인 오류는 제한된 내부 재시도로 복구한다.
3. 정해진 분석 범위 전체의 처리가 성공하면 결과 게시를 진행한다.
4. 최종 실패하면 실패 이유와 대시보드 이동 링크를 안내한다.
5. 사용자가 대시보드에서 재시도를 누르면 성공 결과를 재사용하여 실패 지점부터 재개한다.

Worker 프로세스는 시작할 때 OpenAI 클라이언트를 한 번 생성해 Agents SDK의 기본 클라이언트로 등록하고, 모든 분석에서 공유하다가 종료할 때 닫는다. AI 요청의 일시적인 통신 오류·rate limit·서버 오류는 Agents SDK의 재시도 정책으로 처리한다. 기본 재시도는 최대 2회이며, 최초 호출과 재시도 모두 AI 호출 한도를 먼저 확보한다. Worker와 하위 OpenAI 클라이언트는 모델 요청을 별도로 반복하지 않는다. 인증 오류나 응답 검증 실패는 자동 재시도하지 않는다.

재시도 조건:

- 원래 커밋·설정으로 이어간다. 현재 설정으로 처음부터 다시 분석하는 수동 새 리뷰와 구분한다.
- 현재 PR head가 바뀌었다면 과거 실행 재개를 차단하고 최신 커밋 리뷰로 안내한다.
- Write 이상 권한, App 접근 권한, 전체 중지 여부, 이미 대기·진행 중인 실행을 재확인한다.
- 대시보드 링크를 여는 GET 요청만으로 리뷰가 실행되지는 않는다.
- 권한 상실·전체 중지·입력 부재·처리 한도처럼 같은 요청을 반복해도 해결되지 않는 조건은 이유와 필요한 조치를 안내한다.
- 필요한 저장 자료가 실제로 없다면 재개 불가를 안내한다. 비용이 드는 전체 재분석을 재개로 가장해 자동 실행하지 않는다.

분석은 끝났지만 GitHub 게시가 실패하면 분석을 다시 하지 않고 저장된 결과로 게시를 복구한다. 응답 유실로 게시 성공 여부가 불분명하면 기존 리뷰·댓글의 존재를 확인하여 중복 게시를 막는다. GitHub와 자체 DB를 아우르는 원자적 트랜잭션이나 이미 게시된 결과의 자동 철회를 약속하지 않는다.

대기 취소와 오래된 head 작업 대체는 내부 실행 관리에서 구분한다. 이를 ‘부분 완료’로 표시하거나 정상 리뷰 결과로 집계하지 않는다.

## 7. 대시보드와 통계

대시보드 통계는 다음 두 종류다.

1. 리뷰한 PR 수
2. 게시한 지적 수와 유형별 분포: 버그·보안·스타일·유지보수성

개별 실패 리뷰에는 실패 표시·이유·재시도 기능을 제공한다. 운영과 장애 복구에 필요한 실행 상태는 내부적으로 추적한다.

집계 원칙:

- PR 수와 실행 횟수를 구분한다. 같은 PR의 재시도가 PR 수를 늘리지 않는다.
- 지적 수는 각 리뷰에서 GitHub에 실제 게시한 항목을 기준으로 한다. 수동 새 리뷰에서 다시 게시한 지적은 별도로 집계하고, 같은 실행의 재시도·게시 복구는 중복 집계하지 않는다.
- 미게시 중간 분석 결과는 지적 통계에 포함하지 않는다.
- 코드를 포함하지 않는 통계 기록은 계속 누적한다.

## 8. 자료 보관과 연결 해제

재시도에 필요한 자료를 저장하고, 연결 상태와 사용자 권한에 따라 접근을 제어한다.

| 구분 | 처리 방식 |
| --- | --- |
| 재시도 자료 | 원래 입력·설정·성공한 중간 결과를 저장하고 재사용 |
| 개발·검증 자료 | 재시도 자료를 기한 설정 없이 보관 |
| 통계 기록 | 코드 본문과 구분하여 계속 누적 |
| App·저장소 접근 해제 | webhook 또는 권한 재검증으로 해제를 확인한 즉시 해당 범위의 추가 조회·실행·재시도·게시 차단 |
| 연결 해제 후 기록 | 설정·통계 유지. 재연결 후 권한을 확인하여 복원 |

연결 해제 시 서버 자료는 보존하고 접근과 처리를 차단한다. 필요한 재개 자료가 없으면 재개 불가 사유와 새 리뷰 요청 방법을 안내한다.

## 9. 처리 한도

- 큰 입력도 chunk 단위로 나누어 처리한다.
- 끝없는 실행을 막기 위한 처리 시간·AI 호출·동시 실행·재시도 상한은 운영 설정으로 둔다.
- 실제 분석 부하는 제외 후 코드량, 추가로 읽는 관련 코드, 호출 수에 따라 달라진다.
- 상한 초과를 숨기거나 일부만 분석하고 완료로 표시하지 않는다.

## 10. 완료 기준과 검증 분담

### 기능 구현 및 실제 동작 확인

- 실제 HTTPS 환경에서 GitHub App 설치와 로그인, 개인·조직 및 public·private 저장소의 접근 제어가 동작한다.
- 실제 PR 이벤트가 webhook → 작업 실행 → GitHub 진행 댓글 → 리뷰 결과 게시까지 연결된다.
- `draft=false`인 PR의 `opened` 또는 draft PR의 `ready_for_review` 이벤트가 발생하면, 자동·수동 리뷰 실행 기록이 없는 PR에만 최초 1회 자동 리뷰한다. 수동 리뷰 후 자동 설정을 켜고 `ready_for_review` 이벤트가 발생해도 실행하지 않는다. `synchronize`·리뷰 이후의 `converted_to_draft`·`reopened` 이벤트는 자동 리뷰를 실행하지 않는다.
- 댓글로 요청한 수동 리뷰, 동일·새 커밋의 수동 재리뷰, 공통·독립 설정, 자동 OFF와 전체 중지가 합의한 대로 동작한다.
- 중요한 설명형 인라인과 적용 가능한 suggestion을 확인한다. 사용자 적용으로 PR 브랜치에 반영되는 경로를 확인한다.
- 지적 없음·전체 제외를 서비스 실패와 구분하고, 분석 실패를 완료로 숨기지 않는다.
- 실패 후 대시보드 재시도에서 성공한 분석을 재사용하고 원래 커밋·설정을 유지한다.
- 수동 새 리뷰는 이전에 보고한 문제도 현재 코드에 남아 있으면 다시 게시한다.
- 중복 webhook·동시 요청·Worker 중단·게시 응답 유실 때문에 동일한 리뷰 실행이 중복 생성되거나 같은 실행의 결과가 중복 게시되지 않는다.
- 게시 직전 확인에서 오래된 head SHA를 분석한 결과의 게시를 차단한다. 권한 없는 사용자의 조회·실행과 접근 해제를 확인한 뒤의 추가 접근·게시를 차단한다. 외부 API와의 race condition은 4장의 한계를 기준으로 검증한다.
- 대시보드의 목록·설정·재시도·선택한 두 종류의 통계가 실제 실행 결과와 연결된다.

### 보완할 점

현재 구현에서 확인된 아래 세 항목을 우선순위대로 보완한다. 관련 완료 기준은 해당 문제를 해결하고 확인한 뒤 충족한 것으로 판단한다.

| 우선순위 | 항목 | 현재 문제와 보완 기준 |
| --- | --- | --- |
| 1 | 동시 요청 처리 | GitHub 응답을 기다리는 동안 installation 단위 DB 잠금을 유지하고, 다른 요청의 동기 DB 잠금 대기가 event loop를 막을 수 있다. 외부 조회와 잠금 구간을 분리하고 DB 대기가 event loop를 막지 않도록 보완한다. 같은 PR의 중복 실행 차단을 유지하면서 서로 다른 PR의 동시 요청이 정상 진행되는지 확인한다. |
| 2 | 리뷰에 전달하는 코드 문맥 | 변경 구간을 독립적으로 분석하여 같은 파일의 선언·사용 관계가 끊기고, 함께 변경된 파일도 관련 파일 후보에서 제외된다. 분석 대상 파일의 선언·주변 문맥과 참조하는 변경 파일·타입·프로젝트 설정을 함께 고려하도록 보완한다. 선언과 사용이 떨어진 코드 및 여러 파일에 걸친 변경에서 문맥 누락으로 생기는 오탐·누락을 확인한다. |
| 3 | suggestion의 적용 정확성 | 파일·줄·범위의 기본 유효성만 확인하며 실제 교체 결과의 문법·타입·프로젝트 규칙 충족 여부는 확인하지 않는다. 원문과 교체 범위의 정합성을 보완하고, 코드 문맥 개선 후 실제 적용 결과를 평가하여 추가 검증 범위를 정한다. 함수 전체 교체 코드를 한 줄에 삽입하는 등 코드가 깨지는 사례를 줄이며, 정확한 교체가 불확실하면 설명형 인라인만 게시한다. |

suggestion 보완은 대상 저장소의 코드·테스트·빌드 실행을 제외하는 12장의 정책 안에서 진행한다. 구조화 응답이나 줄 번호 검증만으로 프로젝트 전체의 타입·빌드 성공을 보장하지 않는다.

### 구현·검증 진행 원칙

- 확정된 설계를 기준으로 실제로 동작하는 기능을 구현한다.
- 구현 중에는 꼭 필요한 중간 확인만 수행한다. 테스트는 핵심 경로·권한·실패 복구에 집중하고, 과도한 테스트 작성과 동일 범위의 반복 검증을 피한다.
- 최종 검증은 기능을 연결한 뒤 마지막에 수행한다. 오류나 수정이 생기면 영향을 받는 범위를 다시 확인한다.
- 기능 확인에 사용할 PR 수는 핵심 동작을 확인하는 데 필요한 만큼 선정한다. 하나의 PR에 여러 이벤트를 적용할 수 있다.
- 명확한 문제와 suggestion, 지적 없는 PR, 추가 커밋·재시도 흐름을 확인한다.
- 사용자가 직접 실제 저장소에서 사용할 수 있도록 필요한 환경 변수·App 설정·실행 방법을 간단히 남긴다.
- 실행 사실과 미검증 항목을 구분해 기록한다.
- 작업은 파일 수정으로 반영한다. 스테이징은 사용자가 요청한 경우에만 수행한다.
- 명시적인 요청이 없으면 현재 코드와 설계만 유지한다. 변경 전 데이터·응답 형식·버전의 호환 처리나 이를 위한 분기·변환 코드는 추가하지 않는다.
